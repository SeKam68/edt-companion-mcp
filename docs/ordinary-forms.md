# Работа с обычными (неуправляемыми) формами

Практический цикл для конфигураций, где часть форм — обычные. Что доступно агенту, чего
нет, и как выглядит правка модуля от начала до конца.

## Почему так

EDT конфигурацию с обычными формами импортирует нормально: метаданные читаются, BSL-индекс
строится, управляемые формы работают как обычно. Но саму обычную форму EDT **в модель не
поднимает**: и раскладка, и модуль лежат в бинарном контейнере `Form.oform` в каталоге формы.
Ни `.form`, ни `Module.bsl` там нет, и API чтения контейнера EDT не предоставляет.

Плагин читает этот контейнер сам — и умеет писать в него текст модуля.

Право на запись подтверждено проверкой, а не рассуждением. EDT обычную форму не моделирует, а
везёт её файл как есть и сравнивает содержимое с информационной базой: внешняя правка проходит
валидацию, обновление ИБ её принимает, а откат файла снова переводит базу в состояние
«требуется обновление». Раньше здесь было написано, что модель EDT об изменении не узнает —
это неверно, формулировка перенесена из требований без проверки.

**Раскладка формы по-прежнему только для конфигуратора.** И есть ограничение по существу: см.
«Чего менять нельзя».

На конфигурации эпохи 8.2 речь может идти о половине кода, поэтому важно, чтобы инструменты
не выдавали неполноту за полноту.

## Что доступно

| Инструмент | Поведение по обычной форме |
|---|---|
| `get_config_properties` | `defaultRunMode`, `modalityUseMode`, `interfaceCompatibilityMode` и `formCounts` — сразу видно, с чем имеешь дело |
| `get_object_details` | `formType` у каждой формы объекта |
| `get_form_layout` | `layoutAvailable: false` с причиной, плюс `container` и `modulePath` — раскладки нет, но модуль найден |
| `read_module_source` | текст модуля из контейнера, `source: "oform"` и `writeHint` |
| `get_module_structure` | процедуры и функции с параметрами и диапазонами строк |
| `read_method_source` | текст одной процедуры |
| `search_in_code` | контейнеры досматриваются отдельным проходом; совпадения помечены `source: "oform"`, `openable: false` |
| `write_module_source` | правка текста модуля внутри контейнера; состав процедур менять нельзя |
| `get_form_screenshot` | отказ сразу — рендерить нечего |
| `edit_metadata addForm` | `formType: "Ordinary"` отклоняется |

## Как найти модуль

Путь предсказуемый: каталог формы плюс `Module.bsl`. Файла с таким именем на диске нет —
это адрес, по которому инструменты достают текст из контейнера.

```
/<Проект>/src/<Тип>s/<Объект>/Forms/<Форма>/Module.bsl
```

Если строить путь руками не хочется, его отдаёт `get_form_layout`:

```json
{"name":"get_form_layout","arguments":{"fqn":"Catalog.Контрагенты","formName":"ФормаЭлемента"}}
```
```
Form: Catalog.Контрагенты.Form.ФормаЭлемента [Ordinary]
layoutAvailable: false
Код и раскладка обычных форм хранятся в бинарных Form.oform; EDT их в модель не поднимает; ...
container:  /Демо/src/Catalogs/Контрагенты/Forms/ФормаЭлемента/Form.oform
modulePath: /Демо/src/Catalogs/Контрагенты/Forms/ФормаЭлемента/Module.bsl
```

Заметь: `list_modules` модули форм не перечисляет — ни обычных, ни управляемых, это его общее
свойство. Отправная точка — `get_object_details` или `get_form_layout`.

## Привязка обработчиков и о чём предупредит запись

Обработчик обычной формы указан **по имени процедуры**, а не ссылкой. В раскладке это выглядит так:

```
{70000,e1692cc2-605b-4535-84dd-28440238746c,
{3,"ПередОткрытием",
{1,"ПередОткрытием",
{1,1,
{"ru","Перед открытием"}
```

Раскладка вне модели EDT, поэтому за переименованием процедуры привязка не переезжает:
конфигурация соберётся, база обновится, а событие молча перестанет срабатывать.

Но привязаны далеко не все процедуры. Замер по одной боевой конфигурации: из 4280 процедур в
контейнерах **2993 упомянуты раскладкой**, а **1280 — нет** (это служебные процедуры в 206
формах). Их можно переименовывать, добавлять и удалять свободно.

Есть и второй, менее очевидный путь привязки — **из кода**:
`ПодключитьОбработчикОжидания("ИмяПроцедуры", 1)` или `Выполнить("ИмяПроцедуры()")`. В раскладке
такого имени нет, а ломается оно так же тихо; в том же замере так привязаны 39 процедур из 1280.

Поэтому `write_module_source` считает, какие имена исчезли из модуля, и проверяет каждое по двум
источникам — раскладке и строковым литералам самого модуля:

- **никто не ссылается** → правка проходит молча, в ответе только `methodsChanged`;
- **ссылаются** → правка **всё равно проходит**, но в ответе появляются `warning`,
  `handlerBindingsAffected` (имя, чем привязано, имя события) и `actionRequired`: открыть форму в
  конфигураторе и перепривязать обработчики. Для привязки из кода — поправить строку с именем.

Строгий режим включается на вызов: `handlerChanges: "refuse"` отклоняет такую правку вместо
предупреждения. По умолчанию — `warn`.

Регистр и порядок объявлений изменением не считаются: платформа регистр в именах не различает.

## Цикл правки

1. **Разобраться.** `get_module_structure` по `modulePath` — список процедур с диапазонами
   строк. Дальше точечно `read_method_source`, а не весь модуль целиком.
2. **Править.** `write_module_source` по тому же `modulePath` — доступны все шесть режимов
   (`replace`, `append`, `insertBefore`, `insertAfter`, `replaceLines`, `searchReplace`),
   есть `dryRun`. Текст берётся из контейнера, правится и контейнер собирается заново; прежняя
   версия файла остаётся в Local History EDT. Если правка задела привязанный обработчик, в
   ответе будет `warning` — прочитать его обязательно, молча оно не сломается только в
   служебных процедурах.
3. **Проверить.** Валидация EDT этот код не видит, `get_validation_errors` по нему молчит, —
   значит синтаксис проверяется линтером по тексту, а логика чтением.
4. **`sync_database`.** Без обновления информационной базы правка живёт только в исходниках.
5. **Правка мимо плагина** (в конфигураторе или файловым инструментом) требует
   **`refresh_workspace`**: извлечённый текст кешируется по метке времени файла, а её workspace
   узнаёт только после refresh. Этот же вызов сбрасывает кеши плагина и счётчики форм. После
   записи через `write_module_source` шаг не нужен — она идёт через workspace API.

## Что неполно и чем компенсировать

Раскладка обычной формы вне модели, её модуль вне BSL-индекса. Отсюда:

- `find_object_references` не видит ссылок на метаданные из реквизитов и элементов таких форм;
- `get_method_call_hierarchy` не видит ни вызовов из них, ни объявлений в них;
- `get_validation_errors` не проверяет этот код.

Все три инструмента добавляют в ответ блок `coverage` со счётчиками, когда обычные формы в
проекте есть, — чтобы нуль не читался как «использований нет».

**Перед переименованием или удалением объекта `search_in_code` обязателен**: он единственный
видит и `.bsl`, и контейнеры. Разница бывает существенной — процедура, которая по индексу
выглядит как единственная, на деле может встречаться в нескольких обычных формах.

## Признаки в ответах

| Поле | Значение |
|---|---|
| `source: "oform"` | текст извлечён из контейнера, а не из файла |
| `readOnly` | `true`, только если запись запрещена настройкой (`read` / `off`) |
| `writeHint` | как править и чего нельзя — появляется, когда запись разрешена |
| `container` | путь к `Form.oform`, где физически лежит модуль |
| `openable: false` | позицию совпадения нельзя открыть в редакторе EDT |
| `layoutAvailable: false` | раскладка недоступна; пустых секций в ответе нет намеренно |
| `coverage` | инструмент не покрывает обычные формы; в блоке — сколько их и сколько с кодом |
| `methodsChanged` | правка изменила состав процедур: что исчезло, что появилось |
| `warning` + `handlerBindingsAffected` | исчезли имена, на которые ссылаются: чем привязаны и к какому событию |
| `actionRequired` | что сделать в конфигураторе, чтобы обработчик снова срабатывал |

## Настройка

**Window → Preferences → edt-companion-mcp**, «Обычные (неуправляемые) формы»:

- **авто** (по умолчанию) — чтение и запись, применимость определяется наличием `Form.oform`
  в проекте. На конфигурациях с управляемыми формами вывод инструментов не меняется вовсе;
- **чтение и запись всегда** — не зависеть от эвристики;
- **только чтение** — запись в контейнер отклоняется, чтение остаётся;
- **не читать контейнеры** — аварийное выключение: извлечение текста отключается, но отказы с
  внятной причиной остаются.

Переменная окружения `EDT_COMPANION_ORDINARY_FORMS` (`auto` / `on` / `read` / `off`)
перекрывает настройку — удобно для headless-запусков.

Проверка применимости идёт **по проекту**, а не по workspace: рядом с конфигурацией обычно
открыты расширения, где обычных форм нет.
